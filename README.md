# EviBound: Evidence-Bound Runtime Enforcement for Smart-Home Agents

COSC 723 course project. An AI agent (local Qwen2.5-7B-Instruct) controls a
simulated light and fan from a presence-sensor reading. If the reading it sees
is forged or out of date, a well-formed command can still be unsafe, such as
turning the light on in an empty room. EviBound sits between the agent and the
devices and, before every write, checks that the sensor record the agent cited
is genuine and recent, and that the write obeys the device rules and
permissions. The experiments measure whether this removes unsafe effects while
still letting normal tasks finish. Everything is synthetic and offline: no real
home, device, account or paid API.

**New readers: start with the [Reading Guide](docs/reading_guide.md)**, which
explains the toy world (levels are off / level 1 / level 2), the device rules,
every condition code (B0, B2, M, ...), the metrics and the statistics terms.
For how the simulated attacks map to real homes, see
[Threat Model in the Real World](docs/threat_model_real_world.md).

**The course report** (what was tested, what the research contract's
hypothesis predicted, and which half of it held) is kept locally; it is not
part of this public repository.

## In plain words

**What this is.** A strict doorkeeper for an AI assistant that switches home
devices. Before every switch the assistant has to show the sensor reading it
relied on. The doorkeeper does not take the assistant's word for it. It looks
the reading up in its own trusted records and asks three questions: is this
reading real, is it still fresh, and do the device rules and the user's
permissions allow this switch?

**Why it is needed.** An assistant usually goes wrong not because someone
talked it into something, but because it reasoned correctly from a false
premise. The reading says "someone is home", so it turns the heater on, and
the reading was forged or is from this morning. A guard that only checks
rules is fooled along with the assistant, because it checks them against the
same false reading.

**Does it work.** In the 1,116 attacked episodes of the main study, the guard
that trusts the reading the assistant cites let 134 unsafe actions through.
EviBound let none through. In the first two studies it refused no action
that was legal and backed by fresh evidence. Its cost lies elsewhere: after a
correct refusal the assistant is often bad at repairing its own plan.

**The finding we did not expect.** What should the doorkeeper say after "no"?
We compared seven messages. The friendliest-looking one, a list of everything
that is allowed right now, was the worst. It works like a menu handed to
someone who was not hungry: the assistant orders something. Episodes that end
with a change nobody asked for nearly doubled (850 against 445 of 3,348).
Saying why the action was refused is enough, and a review of the assistant's
own plan helps a little more.

**How far it holds.** A second model (Qwen3-8B), and homes with four and six
devices instead of two, gave the same two results in exploratory runs, and
the list did more harm the bigger the home. Everything is simulated, both
models are small and from one family, and the tasks were generated by
programs. See [Interpretation limits](#interpretation-limits).

The **v3.1** study (2026-11-24) follows up on what v2 and v3 had located: the
cost of the guard lies in what the planner does after a correct refusal. It
holds the guard fixed and varies only the one message the guard sends after a
refusal. Seven messages are compared, from the bare verdict to a complete
sequence of writes, on 372 new tasks; 96 of them form an attack battery in
which nothing has to be done unless the attacked reading is believed
([frozen plan](docs/v3_1_preregistration.md),
[results](docs/v3_1_results.md)). For every task an exhaustive search gives
the best end state the rules and the scope allow, so a message is scored on
whether the home ends exactly there and on whether anything changed that
nobody asked for. Five of the six preregistered claims are supported:

- A list of the writes that are legal now, the aid that v3 had added, does
  harm in either of two wordings. Episodes with a change nobody asked for:
  850 and 831 of 3348 with a list, 445 with the reason alone. A plan that was
  only interrupted ended in the attainable target in 68 and 66 of 182 turns
  with a list, and in 121 with the reason alone.
- No other message is ahead of the reason alone by five points, and saying
  how the interface reads the fresh observation helps when the planner had
  chosen the wrong branch (719 against 679 of 1062 turns).
- Under attack the guard that trusts the cited reading had 134 unsafe effects
  in 1116 episodes and the evidence-bound guard none. Across all seven
  evidence-bound conditions no episode had an unsafe effect or a write
  outside the scope (23,436 episodes).

One claim, taken from the development runs, is not supported. A review of the
planner's own rejected plan did not repair fewer plans than the reason alone;
it ended in the attainable target slightly more often (2584 against 2505 of
3348 episodes). What harms is a list of writes the plan did not contain, not
advice as such; this reading was made after the results.

## Run the checks

One command runs every check that needs no GPU and no data beyond the
repository: the unit tests, the three corpus checkers, all five protocol
freezes, the full pipeline with a scripted planner, and the v3.1 records,
which are recomputed from the committed episode fingerprints. The other
levels, up to a model re-run on another machine, are in
[docs/reproduction.md](docs/reproduction.md).

```bash
bash scripts/reproduce.sh
```

The individual checks:

```bash
PYTHONPATH=src:. python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 scripts/check_scenarios_v2.py
python3 scripts/check_scenarios_v3.py
python3 scripts/check_scenarios_v3_1.py
python3 scripts/freeze_v3_1_prereg.py --verify
```

Model runs need one 24 GB GPU and must be launched inside tmux; see
`scripts/run_v2_main_test.sh` (v2), `scripts/wait_gpu_then_run_v3.sh` (v3) and
`scripts/run_v3_1.sh` (v3.1).

## Interpretation limits

The device rules are synthetic policies for the experiment, not real safety
codes. B2 is a guard built for this project, not a reproduction of a published
system. Attacks are fixed value tampering and stale-record replay plus
unauthorized-device requests; prompt injection, trained backdoors and adaptive
attackers are out of scope. Record matching stands in for cryptographic sensor
authentication.

# 中文说明

COSC 723 课程项目。AI 智能体（本地 Qwen2.5-7B-Instruct）根据人体存在传感器的
读数控制模拟的灯和风扇。如果它看到的读数是伪造的或过时的，一条格式正确的
命令也可能不安全，比如在没人的房间开灯。EviBound 放在智能体和设备之间，
每次写设备前核对智能体引用的传感器记录是否真实、是否足够新，以及这次写入
是否符合设备规则和权限。实验衡量它能否消除不安全后果，同时不耽误正常任务。
全部为离线合成实验，不连接真实家居、设备或账号，不调用付费 API，不训练模型。

**第一次读请先看[阅读指南](docs/reading_guide.md)**：解释档位（关 / 1 档 /
2 档，`low` 不是“调暗”）、设备规则、各条件代号（B0、B2、M……）、指标和统计
术语。模拟攻击在真实家庭中对应什么，见[威胁模型的现实对应](docs/threat_model_real_world.md)。

## 三分钟读懂

**这个工作做了什么。** 给控制家电的 AI 助手配了一个较真的门卫。助手每次要动设备，都得出示它依据的那条传感器读数。
门卫不听助手怎么说，自己去可信的记录里核对三件事：这条读数是真的吗？还新鲜吗？这次操作符合设备规则和用户授权吗？
三件事都过了才放行。

**为什么需要它。** 助手出事，往往不是被人说服去做坏事，而是对着错误的前提做了正确的推理：读数说“有人在家”，它就把暖气打开了，
可这条读数是伪造的，或者是今天早上的。只查规则的守卫会跟着助手一起上当，因为它查的也是那条假读数。

**管用吗。** 主实验的 1,116 个受攻击回合里，相信助手所引读数的守卫放过了 134 次不安全操作，EviBound 一次也没有。
前两个实验里，它也没有拦过任何一次合规且证据新鲜的操作。它的代价在别处：被正确拦下之后，助手常常修不好自己的计划。

**没想到的发现。** 门卫说了“不行”之后，该跟助手说什么？我们比较了七种说法。看起来最贴心的那种，附上一张“现在还能做哪些操作”的清单，
结果最差：像把菜单递给一个并不饿的人，他多半还是会点点什么。出现没人要求的改动的回合几乎翻了一倍（850 对 445，共 3,348 个）。
把“为什么不行”说清楚就够了；再帮助手看一眼它自己的计划，效果还能好一点。

**靠得住吗。** 换一个模型（Qwen3-8B），再把家从 2 个设备扩大到 4 个和 6 个，这两个结论在探索性实验里都还在，
而且家越大，清单的害处越大。全部是模拟环境，两个模型都不大、来自同一个家族，任务由程序生成。详见下文“解释边界”。

这次守卫本身完全不变，只改它在拒绝之后发给规划器的那一条消息。共比较七种消息，从只给判定到直接给出一串写入；
372 个新任务，其中 96 个是“攻击电池”：除非相信被攻击的读数，否则什么都不用做
（[冻结的计划](docs/v3_1_preregistration.md)、[结果](docs/v3_1_results.md)）。每个任务都用穷举搜索算出规则和授权之内的最好结局，
所以每种消息按两点打分：家里最后是否正好停在那个结局上，以及有没有出现没人要求的改动。六条预注册主张中五条成立：

- v3 加入的“合法写入清单”有害，两种措辞都一样。出现没人要求的改动的回合：有清单时 850 和 831 / 3348，只说原因时 445。
  只是被打断的计划，最后停在可达目标上的：有清单时 68 和 66 / 182，只说原因时 121。
- 没有任何其他消息领先“只说原因”达到五个百分点；规划器选错分支时，说出界面如何读取新读数有帮助（719 对 679 / 1062）。
- 受攻击时，相信被引用读数的守卫在 1116 个回合中出现 134 次不安全后果，证据绑定的守卫为零。七个证据绑定条件下
  没有任何回合出现不安全后果或越权写入（共 23,436 个回合）。

有一条来自开发实验的主张不成立：对规划器自己被拒绝的计划做复核，并没有比只说原因修好更少的计划，
反而略多（停在可达目标上的回合 2584 对 2505 / 3348）。有害的是把计划里没有的写入列给规划器，而不是“给建议”本身；
这一解读是看到结果之后做出的。

## 运行检查

一条命令跑完所有不需要显卡、也不需要仓库以外数据的检查：单元测试、三个语料检查、全部五个
协议冻结、用脚本规划器走一遍完整流水线，以及从已提交的逐回合指纹重算 v3.1 的各项记录。其余层级
（直到在另一台机器上重跑模型）见[复现说明](docs/reproduction.md)。

```bash
bash scripts/reproduce.sh
```

单项检查：

```bash
PYTHONPATH=src:. python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 scripts/check_scenarios_v2.py
python3 scripts/check_scenarios_v3.py
python3 scripts/check_scenarios_v3_1.py
python3 scripts/freeze_v3_1_prereg.py --verify
```

模型运行需要一张 24 GB 显卡，并在 tmux 里启动：v2 见
`scripts/run_v2_main_test.sh`，v3 见 `scripts/wait_gpu_then_run_v3.sh`，v3.1 见 `scripts/run_v3_1.sh`。
v1 的 30 回合复现子集仍可用 `bash scripts/reproduce_subset.sh` 运行，它只验证
管线，不能替代完整统计。精确依赖版本见 `artifacts/environment_v2.json` 和
`configs/requirements_observed.txt`。

## 解释边界

设备规则是课程实验的合成策略，不是真实安全规范。B2 是本项目自建的守卫，
不是已发表系统的复现。攻击仅包括固定的读数篡改、旧记录重放和越权设备请求；
不包括提示注入、训练后门或自适应攻击者。“记录精确匹配”代替的是密码学传感器
认证。
